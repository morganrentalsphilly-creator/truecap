## Phase 1 — Stop the revenue leak (branch `billing-fix`)

**Root cause, stated plainly.** The Stripe account is shared with Philly Rental Compliance. Every event on the account reaches TrueCap's webhook. Two failure classes followed: (1) foreign renewals hit the binding code and paged Sentry at error level ("cannot resolve verified user for unbound customer" — 94 times on 2026-08-31, all the other product's); (2) a TrueCap event that carried only an email, or whose `client_reference_id` was dropped, had no path to a user and was skipped with a categorical Sentry message and nothing durable. The customer paid, the entitlement never landed, and there was no row to act on.

### Decisions made in the founder's absence (Phase 1)

1. **Foreign-app guard added.** Not in the brief, but without it the ordered resolver's email step would have bound the other product's customers to TrueCap accounts whenever an email matched, and every one of its renewals would have become an "unresolved" row plus an error-level page. Conservative choice: skip quietly, stamp the ledger row, never bind. An unknown price is treated as foreign only when the object also carries no TrueCap marker and its customer is unbound — that keeps the 2026-07 unmapped-price incident class inside the recovery ladder.
2. **`metadata.user_id` accepted at the same rank as `metadata.supabase_user_id`.** Checkout has stamped `user_id` with the identical value since the first release, and every in-flight session was created before this change. Treating it as a lower-ranked signal would have made the very next renewal go through the email step for no reason.
3. **Migration apply is founder-owed.** No database credential is exportable from this machine (every Vercel env value is Sensitive, there is no Supabase CLI and no connection string, and the MCP connector exposes only the other project). The code tolerates the missing table, so nothing waits on it — but until the SQL is applied, unresolved reasons live on `stripe_webhook_events.error_message`. SQL to run in the Supabase SQL editor: `supabase/migrations/20260906170000_billing_unresolved_events.sql`.
4. **The reconcile runs inside production as a cron, dry by default.** The brief says "run `scripts/billing-reconcile.ts` in dry-run mode against the test key, then apply". There is no test key here and no production key either, so the same core also runs as `/api/cron/billing-reconcile` daily at 17:30 UTC with the real env. `BILLING_RECONCILE_MODE` defaults to `dry` (counts only, zero writes) because that is the safe unattended behaviour; `apply` needs the founder to set the env var. Results are counts only, in the Vercel runtime log line `[cron/billing-reconcile] {...}`, in a Sentry message, and in the JSON response.
5. **No summary email.** The hard limits allow one outbound email in the whole run (the guarded Phase 5 feedback request). A reconcile summary email would be a second, so the cron reports through logs and Sentry instead.
6. **No `package.json` script alias for the CLI.** `package.json` is in the build-integrity manifest; a manifest bump for a convenience alias is not worth the extra guarded commit. The exact invocation is in the script header and below.
7. **Middleware cookie clearing is scoped to dead-session codes only.** The earlier comment in that file argued for never clearing on a throw because a transient outage looks the same; that stays true for the throwing class. For the non-throwing class auth-js returns a structured code, so the two are distinguishable and only the dead ones clear.
8. **`vercel.json` edit** puts this change in the build-chain integrity guard; the manifest is bumped in its own commit, as the guard requires.
